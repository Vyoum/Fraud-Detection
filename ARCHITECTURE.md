# Architecture

## Pipeline overview

![Pipeline architecture](docs/architecture.svg)

```
train_transaction.csv + train_identity.csv
        |
        v
entities.py       resolve_entities()      -> uid per TransactionID (persistent client identity)
        |
        v
evaluate.py        temporal_train_test_split()   -> train_df, test_df (last 20% by TransactionDT)
        |
        v
graph.py            build_entity_graph(train_df, ...)         -> EntityGraph (nodes=uids, edges=linkage rules)
                     compute_cluster_features(train_df, ..., as_of=test.min()) -> per-uid cluster features
        |
        v
model.py             build_feature_matrix() + train_baseline_model() / train_cluster_model()
        |
        v
evaluate.py          evaluate_model()        -> PR-AUC, recall@1%FPR, cost per 10k (frozen metrics module)
        |
        v
policy.py            decide() / apply_policy()   -> allow / step_up / review, from fixed cost-derived thresholds
        |
        v
investigator.py       explain_cluster()       -> LLM narrative, grounded in the same evidence policy.py never reads
```

Every stage after `entities.py` depends only on data with `TransactionDT`
strictly earlier than whatever it's scoring -- see "Causal feature
computation" below. `run_pipeline.py` is the only module that wires these
together; none of the others import each other's orchestration logic (see
"ML / LLM / policy boundary").

## Batch vs. inline

This is the split that actually matters for latency and cost, stated
plainly rather than left implicit in the code:

| Stage | When | Why |
|---|---|---|
| `resolve_entities` | batch | Needs the full transaction history to derive a stable uid; not meaningful per-request. |
| `build_entity_graph` | batch | Rebuilt from all train-period transactions; O(minutes) at this scale, and correctness depends on seeing the whole linkage graph at once (see max_degree below). |
| `compute_cluster_features` | batch | Same reason -- a cluster's features depend on all its members' history up to `as_of`, computed once and cached, not recomputed per transaction. |
| Transaction scoring (`model.predict`) | **inline** | Given a transaction, look up its uid's precomputed cluster features (a cache/feature-store read, not a recomputation) and call the model. This is the only step on the request path. |
| `policy.decide` | inline | A pure score-vs-threshold comparison; O(1), no I/O. |
| `investigator.explain_cluster` | **not on the request path at all** | Called for investigation/audit purposes on a cluster an analyst is already looking at, not per-transaction. Its own latency (an LLM API round-trip) would be unacceptable inline. |

Measured, real figures in the "## Performance" section at the bottom of
this file (regenerated by every `make results` run, not hand-copied here):
graph construction and cluster feature computation together take single-digit
seconds for the full train set; inline per-transaction scoring is tens of
milliseconds p50. Two very different latency budgets -- roughly three
orders of magnitude apart -- which is exactly why they're on opposite
sides of this split.

## Linkage rules and their rationale

Nodes in the entity graph are uids. Two uids are linked when they share a
value on one of three rules (`src/graph.py`, `LINKAGE_RULES`):

| Rule | Key columns | Rationale |
|---|---|---|
| `device_info` | `DeviceInfo` | The exact same device fingerprint across multiple client identities is strong evidence of a shared physical device -- one operator running several card+address combinations, or a device farm. |
| `addr1_email` | `addr1`, `P_emaildomain` | A shared delivery/billing address code AND a shared purchaser email domain together are stronger than either alone: many people share a common email provider, and many share a common region-coded addr1 value, but the co-occurrence of both narrows this considerably. |
| `card_bank_addr` | `card3`, `card5`, `addr1` | card3/card5 are issuing-bank/network category codes that are essentially fixed once card1 is fixed (confirmed empirically: they never varied across the 20 largest uids in the collision check, see results/d1_investigation.md). Requiring them to match jointly WITH addr1 links different card1 values sharing the same issuer/network profile and address. |

**Hub guard.** A value shared by an enormous number of uids (`"Windows"`,
`"gmail.com"`) is a common default, not evidence of a relationship.
`build_entity_graph` excludes any value shared by more than `max_degree`
uids from linkage entirely, and reports what it excluded
(`results/ablation.md`'s "Graph construction" section).

**Why `max_degree=20`, not the function's own default of 1000.** Found
empirically: addr1 is a region-level code (a few hundred distinct values
across ~524k uid'd rows) and card3/card5 are almost constant (dominated by
150.0/226.0), so `card_bank_addr` is close to a proxy for addr1 alone.
Sweeping `max_degree` on the real data: 20 -> largest cluster 126 uids
(0.06% of all uids); 30 -> 919 (0.46%); 35 -> 5,141 (2.58%); 1000 (the
literal default) -> 127,708 uids in one connected component (**64%** of
everything). The transition between 30 and 35 is sharp, not gradual. What
this excludes at max_degree=20: 1,114 values covering 376,264
uid-appearances, dominated by generic device strings (`Windows`: 18,535
uid appearances; `iOS Device`: 12,719; `MacOS`: 8,344) and the most common
addr1+email / card-profile combinations. The trade-off is explicit: a
higher `max_degree` would catch a few more genuine large rings, but the
real cost is a single supercluster that makes cluster-level features
nearly constant across the whole population -- worse than missing some
larger rings.

## Causal feature computation, and why it matters

Per CLAUDE.md: "Cluster features must be computed causally. Graph
structure and aggregates for a test transaction may only use transactions
with strictly earlier TransactionDT." Concretely:

- `build_entity_graph` is called on `train_df` only -- `test_df` is never
  passed to it, so no test-period transaction can ever contribute an edge
  or a node.
- `compute_cluster_features` filters every transaction-level aggregate
  (velocity, amount CV, burst concentration, email heterogeneity,
  prior-fraud share) to `TransactionDT < as_of` internally, where `as_of`
  is the first test-period timestamp -- so both train and test rows get
  cluster features computed from the same pre-boundary snapshot, and nothing
  from the test period ever leaks into a feature used to score it.

This isn't a theoretical property -- it's the single most likely place a
lift number could be an illusion, and it was checked against the real
data, not just the code: all 155,579 clusters with a reported
`cluster_prior_fraud_share` were independently recomputed straight from
raw rows restricted to `TransactionDT < as_of`, bypassing `graph.py`
entirely. Zero mismatches (`results/ablation.md`'s Sanity checks section).
`tests/test_graph.py` also has an explicit unit-level leakage test: a
transaction dated after `as_of`, with a fraud label and amount specifically
chosen to change every cluster feature if it leaked in, must not change any
of them.

## ML / LLM / policy boundary

CLAUDE.md's rule: "The LLM layer explains and prioritizes. policy.py
decides. Never merge them." Enforced structurally, not just by convention:

- `policy.py` has **no import of `investigator.py`** -- checked two ways
  in `tests/test_policy.py`: statically (parse `policy.py`'s AST, assert no
  import mentions "investigator") and behaviorally (`apply_policy` on
  identical scores with `ANTHROPIC_API_KEY` set vs. unset, and
  `sys.modules["src.investigator"]` simulated unavailable -- identical
  output both times).
- `policy.decide()`'s only input that determines the action is the model
  score against two fixed, cost-derived thresholds
  (`STEP_UP_THRESHOLD=0.0103`, `REVIEW_THRESHOLD=0.1843` -- read from real
  cost-curve sweeps, see `scripts/derive_policy_thresholds.py`, not
  hand-picked). It accepts `cluster_features` as an argument but never
  uses it in the comparison -- documented explicitly in its own docstring
  so this isn't mistaken for a bug.
- `investigator.py` produces a narrative and a `priority_score` for
  ranking an investigation queue. It never determines allow/step_up/review,
  and its output is not fed into `policy.decide()` anywhere in the pipeline.
- The dashboard (`app.py`) makes this visible at the UI level too: every
  decision shown is explicitly labeled as coming from policy.py with the
  threshold that produced it, and every narrative is labeled with its real
  source (`llm` or `ungrounded-fallback`) -- an analyst should be able to
  tell at a glance which part of the screen a model produced and which
  part a language model produced, not just trust that the architecture doc
  says so.

## Performance notes

The optional Kafka/Hadoop path is described in [docs/STREAMING.md](docs/STREAMING.md).
`src.streaming.export` creates a versioned serving bundle from this research
pipeline. Kafka workers score observations using that frozen bundle and commit
decisions with input offsets; a SQLite projection serves the live dashboard.
Spark archives events into HDFS and prepares explicitly labeled historical
Parquet for later batch runs. Graph construction and training remain local,
and the existing training/threshold-selection limitations still apply.

## Performance

Batch/inline split, stated plainly: graph construction and cluster feature computation are BATCH -- run periodically (e.g. nightly, or whenever the graph is rebuilt) against historical/train-period transactions, never on the request path. Transaction scoring is INLINE: given a transaction, look up its uid's precomputed cluster features (a cache/feature-store read, not a recomputation) and call the model. Below is measured separately because they answer different capacity questions --  batch steps bound how often the graph can be refreshed, the inline step bounds request latency.

### Batch: graph construction and cluster features

- Graph construction (472,432 train-period transactions, max_degree=20): **6.64s** (167,111 nodes, 62,804 edges)
- Cluster feature computation (167,111 uids): **19.71s**

### Inline: per-transaction scoring latency

1,000 single-transaction scoring calls (feature-store lookup + model.predict on one row), sampled from the real test set:

| stat | value |
|---|---:|
| p50_ms | 51.897 ms |
| p95_ms | 58.132 ms |
| p99_ms | 65.449 ms |
| mean_ms | 52.416 ms |
| max_ms | 82.291 ms |

This is single-row prediction, not batched -- LightGBM's per-call overhead dominates at this granularity, so p95 here is a meaningfully worse number than the model's throughput in bulk scoring would suggest. A real inline path would likely batch several in-flight requests if the volume justified it.

### What would need to change at ~1B transactions/quarter

This benchmark's full graph build (472,432 transactions) took 6.64s for construction + 19.71s for features. ~1B transactions/quarter is roughly 2117x this benchmark's train set. Naive linear scaling alone would already push a full rebuild from seconds into hours, and the real cost is worse than linear: this project's own hub-guard investigation (graph.py's module docstring) found that the graph's structure is sensitive to `max_degree` in a highly non-linear way (a phase transition, not a smooth curve) -- at greater scale, more identifier values cross the hub threshold, and getting this wrong risks the same giant-component collapse found earlier this project, at a much more expensive scale to detect and recover from.

Three changes this scale would require, none implemented here:

- **Incremental graph updates instead of full rebuilds.** This project rebuilds the whole graph from all train-period transactions every time (build_entity_graph has no notion of "since last run"). At 1B/quarter, a full rebuild needs to become an incremental one: new transactions add nodes/edges to an existing graph, without re-scanning historical data that hasn't changed.
- **Approximate connected components.** get_connected_components is an exact, single-machine networkx computation. At this scale the graph itself likely needs to be sharded/distributed, and exact connected components across shards is expensive; approximate or incremental union-find structures (as used in large-scale graph processing systems) trade a small amount of accuracy for tractability.
- **Sharding.** The current implementation holds one in-memory networkx graph and one in-memory feature table for the whole dataset. Neither fits in memory on one machine at this volume; the graph and its features would need to be partitioned (e.g. by a hash of a linkage key) across multiple machines, which changes how cross-shard edges (a device or address linking uids in different shards) get detected and reconciled -- a real design problem, not a configuration change.
